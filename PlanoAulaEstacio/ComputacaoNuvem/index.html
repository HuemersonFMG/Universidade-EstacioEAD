1. Visão Geral do Ambiente

Uma organização pode utilizar simultaneamente infraestrutura física local, servidores hospedados externamente, aplicações próprias e softwares contratados como serviço.

Por isso, os conceitos de On-Premises, IaaS, PaaS e SaaS não são necessariamente concorrentes. Eles podem coexistir dentro da mesma arquitetura.

ORGANIZAÇÃO │ ├── INFRAESTRUTURA LOCAL │ └── On-Premises │ ├── INFRAESTRUTURA CONTRATADA │ └── IaaS │ ├── PLATAFORMA GERENCIADA │ └── PaaS │ └── SOFTWARE PRONTO └── SaaS
Pergunta principal:

Para classificar corretamente um serviço, devemos observar qual camada está sendo entregue pelo provedor e qual camada permanece sob responsabilidade do cliente.

On-Premises representa uma infraestrutura instalada fisicamente nas dependências da própria organização.

4. IaaS - Infrastructure as a Service

IaaS significa Infraestrutura como Serviço.

O provedor disponibiliza recursos como processamento, memória, armazenamento, rede e virtualização.

PROVEDOR │ ├── Datacenter ├── Hardware ├── Armazenamento ├── Rede física └── Virtualização │ ▼ CLIENTE │ ├── Sistema Operacional* ├── Configurações* ├── Aplicações └── Dados * A divisão exata depende do serviço contratado.
Atenção:

Contratar um servidor na nuvem não transfere automaticamente toda a responsabilidade de segurança ao provedor.

7. Contêineres

Contêineres permitem empacotar aplicações juntamente com suas dependências em ambientes isolados.

SERVIDOR │ └── SISTEMA OPERACIONAL │ └── CONTAINER ENGINE │ ├── Container A │ └── Aplicação A │ ├── Container B │ └── Aplicação B │ └── Container C └── Aplicação C

Leveza

Normalmente utiliza menos recursos que uma VM completa.

Portabilidade

Facilita transportar aplicações entre ambientes compatíveis.

Isolamento

Processos podem executar separadamente.

Velocidade

Inicialização normalmente rápida.

Máquina Virtual × Contêiner

Característica VM Contêiner
Sistema Operacional Possui sistema próprio. Normalmente compartilha o kernel do host.
Recursos Maior consumo. Geralmente menor.
Inicialização Mais lenta. Mais rápida.
Uso Ambientes completos. Aplicações, APIs e microsserviços.

8. PM2, Máquina Virtual e Contêiner

PM2 não é hypervisor e também não é uma plataforma de contêineres.

PM2 é um gerenciador de processos para aplicações Node.js.

SISTEMA OPERACIONAL │ └── Node.js │ └── PM2 │ ├── App A ├── App B ├── App C └── App D
Tecnologia Função
PM2 Gerenciar processos Node.js.
Docker Criar e executar contêineres.
Hypervisor Criar e administrar máquinas virtuais.

9. Serverless e FaaS

Serverless é uma abordagem em que o desenvolvedor executa código sem administrar diretamente os servidores responsáveis pela execução.

Atenção:

Serverless não significa ausência de servidores.

Significa que a administração da infraestrutura fica amplamente abstraída pelo provedor.

FaaS - Function as a Service

Evento
→
Função
→

→

Eventos podem incluir requisições HTTP, mensagens de fila, alterações em dados, uploads e agendamentos.

10. Banco de Dados Gerenciado

Em um serviço de banco gerenciado, o provedor assume parte relevante da administração da infraestrutura necessária para executar o banco.

Infraestrutura

Recursos computacionais são administrados pelo provedor.

Atualizações

Parte das atualizações pode ser automatizada.

Backup

Pode existir backup gerenciado conforme o plano.

Escalabilidade

Recursos podem ser ajustados conforme demanda.

Segurança:

Banco gerenciado não elimina a responsabilidade do cliente sobre usuários, permissões, credenciais, classificação e utilização dos dados.

Classificação

14. Redes e Segurança da Informação

Uma aplicação publicada na Internet depende de diversas camadas de segurança.

Princípios fundamentais

Confidencialidade

Informações devem ser acessadas somente por pessoas autorizadas.

Integridade

Dados não devem ser alterados indevidamente.

Disponibilidade

Sistemas devem estar disponíveis quando necessários.

Controle de Acesso

Usuários devem possuir apenas as permissões necessárias.

HTTPS / TLS

HTTPS utiliza TLS para proteger a comunicação entre cliente e servidor.

Proteção Principal função

15. Segurança no Desenvolvimento e Liberação para Produção

Para um desenvolvedor de aplicações e páginas web, segurança deve fazer parte de todo o ciclo de desenvolvimento.

Princípio fundamental:

Uma aplicação não se torna segura simplesmente porque está instalada em um servidor protegido.

Segurança precisa ser aplicada ao código, dependências, dados, autenticação, comunicação, infraestrutura, implantação e monitoramento.

Categorias de testes

Testes Funcionais

Verificam se as funcionalidades executam corretamente suas regras de negócio.

  • login;
  • cadastros;
  • consultas;
  • botões;
  • integrações;
  • retorno das APIs.

Testes Não Funcionais

Avaliam características além da funcionalidade.

  • desempenho;
  • carga;
  • estabilidade;
  • compatibilidade;
  • usabilidade;
  • disponibilidade.

Testes de Segurança

Procuram vulnerabilidades e comportamentos inseguros.

  • controle de acesso;
  • injeção;
  • XSS;
  • falhas de autenticação;
  • segredos expostos;
  • dependências vulneráveis.

Tipos de testes de segurança

Tipo Significado O que verifica
SAST Static Application Security Testing Analisa o código-fonte sem precisar executar a aplicação.
SCA Software Composition Analysis Analisa bibliotecas, pacotes e dependências.
Secret Scanning Verificação de segredos Procura tokens, chaves e credenciais expostas.
DAST Dynamic Application Security Testing Testa uma aplicação que está executando.

Security Gate

O pipeline pode impedir automaticamente uma publicação quando uma verificação obrigatória falha.

Por exemplo: vulnerabilidade crítica, teste obrigatório com erro ou segredo exposto.

Responsabilidades do desenvolvedor

Validação

Nunca confiar diretamente nos dados enviados pelo cliente.

Autenticação

Identificar corretamente quem está acessando.

Autorização

Determinar quais recursos cada usuário pode acessar.

SQL Seguro

Utilizar consultas parametrizadas e evitar concatenação insegura.

Segredos

Não armazenar senhas, tokens e chaves diretamente no código.

Dependências

Acompanhar bibliotecas e vulnerabilidades.

Logs

Registrar eventos importantes sem expor dados sensíveis.

Erros

Não revelar detalhes internos desnecessários ao usuário.

Rate Limiting

Limitar requisições suscetíveis a abuso.

Testes

Validar alterações antes da produção.

Rollback

Planejar como retornar para uma versão estável.

Monitoramento

Acompanhar a aplicação após o deploy.

Checklist antes de liberar para produção

  • Git: versão corretamente registrada.
  • Build: processo concluído sem erros.
  • Testes: funcionais e não funcionais aprovados.
  • Segurança: verificações executadas.
  • Dependências: vulnerabilidades avaliadas.
  • Segredos: nenhuma credencial no código.
  • HTTPS: comunicação externa protegida.
  • Autenticação: usuários identificados corretamente.
  • Autorização: usuário acessa apenas aquilo que possui permissão.
  • Validação: entradas verificadas no backend.
  • SQL: consultas implementadas de forma segura.
  • Rate Limiting: utilizado onde necessário.
  • Erros: detalhes internos não são expostos.
  • Logs: eventos importantes registrados.
  • WAF: necessidade e responsabilidade avaliadas.
  • Firewall: apenas portas necessárias abertas.
  • Backup: cópia e restauração verificadas.
  • Rollback: procedimento conhecido.
  • Monitoramento: aplicação acompanhada após o deploy.

PROVEDOR │ └── Infraestrutura, datacenter, hardware, virtualização e serviços contratados TI / SEGURANÇA │ └── Rede, firewall, servidores, acessos, WAF e políticas DESENVOLVEDOR │ └── Código, aplicação, validação, autenticação, autorização, dependências, testes, integrações e logs EMPRESA │ └── Regras de negócio, usuários, classificação dos dados e permissões SEGURANÇA │ └── Resultado da combinação de todas as camadas
Fluxo final para memorizar:
DESENVOLVER ↓ VERSIONAR ↓ INTEGRAR ↓ ANALISAR ↓ TESTAR ↓ HOMOLOGAR ↓ PUBLICAR ↓ MONITORAR ↓ CORRIGIR ↓ NOVO CICLO
Conclusão:

Segurança de aplicações não é responsabilidade exclusiva do provedor, da infraestrutura ou do desenvolvedor.

É uma responsabilidade compartilhada, na qual cada participante precisa conhecer e proteger as camadas que estão sob seu controle.
